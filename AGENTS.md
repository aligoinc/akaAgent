## Bắt buộc dùng skill cho RPC migration

Mọi task tạo, sửa, review hoặc apply SQL có `CREATE OR REPLACE FUNCTION`, `DROP/ALTER FUNCTION` hay thay đổi RPC **bắt buộc** dùng skill [`safe-supabase-rpc-migration`](.agents/skills/safe-supabase-rpc-migration/SKILL.md) trước khi dựng body SQL. Không được lấy body từ migration cũ trước khi đã đọc đúng signature đang chạy bằng `pg_get_functiondef()` và thêm preflight checksum fail-closed.

### Webview controller

[src/main/playwright/webviewController.ts](src/main/playwright/webviewController.ts) — thin wrapper exposing `isConnected()` + `getURL()` cho `webContents` của Electron `<webview>` đã embed cho từng tài khoản FB. Visible webviews vẫn dùng cho login, status checks và test thủ công trong editor.

`WebviewRegistry` maps `accountId -> webContentsId`. Scheduler uses `isRegistered()` to ensure the account has mounted a browser tab at least once; accountPoller uses `listRegistered()` to skip dead tabs. Runtime uses `accountId` and partition `persist:account_${accountId}`; browser profiles from the previous partition prefix are not reused. For browser-based accounts, account proxy is prepared by `ProxyRuntimeService` on this same partition before background page loads and when user manually reloads visible webview; editing/assigning proxy only saves DB and must not auto-reload, close connections, or destroy visible/background pages. Account context actions "Hiển thị & xem trang web" and "Load lại trang web" must ensure BrowserPage opens/mounts the visible webview when `WebviewRegistry` has no tab yet; do not surface "Tab trình duyệt chưa được mở" for these user-triggered open/reload actions.
Khi tạo mới tài khoản Facebook trong `AccountPanel`, không tự chuyển trang ngay; hiển thị alert thành công với CTA duy nhất "Đăng nhập FB", chỉ khi user bấm CTA mới gọi `onNavigateToBrowser({ accountId, reloadAfterOpen: true })` để mở đúng tab BrowserPage cho login.
Thẻ tài khoản trong `AccountPanel` ưu tiên màu theo thứ tự: `đang chạy` vàng → vô hiệu hóa xám → checkpoint/có action bị hạn chế tím → chưa đăng nhập hoặc tạm dừng đỏ → đã đăng nhập và chờ xử lý xanh. `listAccounts()` enrich cờ `hasDisabledActions`; click trái/Enter/Space trên thẻ mở tab `Tài khoản` ở vị trí thứ hai trong detail dock của `CampaignPanel`, không mở modal và không đổi campaign đang focus. Context của tab này độc lập: click thẻ dùng tài khoản vừa click, còn focus campaign dùng tài khoản chính của campaign; chỉ đổi tab qua lại không được ghi đè context. Mục `Thông tin tài khoản` trong menu chuột phải vẫn mở modal. Chiến dịch đang chạy trên thẻ hiển thị bằng icon Play + tên rút gọn.

Convention quan trọng (xem memory `campaign_conventions.md`):
- **C# Facebook DOM workflow reference**: khi user cung cấp code C# Facebook automation đã chạy đúng, xem code C# là source-of-truth cho mọi tương tác DOM trong workflow. ### Workflow engine v2

[src/main/v2/runtime/](src/main/v2/runtime/) — engine duy nhất chạy campaign:
- `workflowEngine.ts` — DAG executor cohort-based: parallel split (multiple outgoing edges), AND/OR join (mode='all'/'any' merge node), `ifElse` skip propagation, loop body re-exec với `vars.loopItem`/`vars.loopIndex`, `AbortSignal` cancellation. `allSteps[]` track loop iterations để scheduler log đầy đủ (snapshot `nodeStates` chỉ giữ iteration cuối).
- `blockExecutor.ts` — `vm.createContext` sandbox. KHÔNG expose `process`/`require`/`Buffer`/`fs`. Block code = JS string, return object → output, throw → fail.
- `pageController.ts` — wrap `webContents.executeJavaScript` thành API `page.click/type/fill/focus/paste/insertText/scroll/evaluate/$$/waitForSelector/uploadFile/dropFile/dropFileDeep/apiCall/downloadUrl`. Hỗ trợ XPath union `|` và CSS. Có fallback scroll cho FB comment box lazy-render; `dropFileDeep` tìm drop target cả trong iframe cùng origin.
- `backgroundPageManager.ts` — hidden/offscreen browser pages cho scheduler, shared persistent partition với visible webview theo account.
- `blockHelpers.ts` — `sleep`/`log`/`randomBetween`/`normalizeFbUrl`/`extractUidFromInput`/`splitVariants`/`cycleVariant`/`element(name)`/`elementWith(name, vars)`/`checkGroupPendingContent(opts)`. `element` query cached `auto_elements`; `checkGroupPendingContent` do scheduler inject runtime helper, mở temporary background page cùng partition account và stream preview page phụ. Helper mở rộng để block DB ghi log cấu trúc phải dùng optional names như `logRunEvent`/`logRunEvents`; nếu runtime chưa implement thì helper trả unsupported/no-op, còn helper sai tên ngoài whitelist vẫn lỗi để bắt typo. Khi helper được implement, engine tự bơm metadata `run_id`/`run_step_id`/`node_id`/`block_name`/campaign/input/account vào `auto_campaign_run_events`; block chỉ truyền event payload.
- Node config runtime `screenshotCaptureTiming` + `screenshotCaptureOn` là metadata universal của workflow engine, không truyền vào `input` block và không ghi vào step output. Phase hiện tại chỉ capture sau block; PNG lưu local dưới `app.getPath('userData')/local-data/block-screenshots`, metadata user-facing ghi vào `auto_campaign_run_events.event_type='browser_screenshot'` với `debug_data.screenshotPath`. Screenshot event metadata lưu kết quả chiến dịch/action dễ hiểu (`Đăng bài thất bại...`, `Lỗi đăng bài...`, policy `auto_error` nếu có); `block_name/node_id` chỉ là metadata debug, không làm text chính cho user.
- Built-in `fb_resolve_url` resolves URL input in this order: `input.raw`, `vars.inputDataUid`, `vars.targetUrl`. DB rows are the source of truth for built-in blocks/workflows/elements.
- Bảng: `auto_blocks`, `auto_workflows`, `auto_elements`, `auto_runs`, `auto_run_steps` (BIGSERIAL id, UNIQUE name).

[campaignScheduler.ts](src/main/services/campaignScheduler.ts) chọn workflow theo current staff: `org_staff.use_test_workflow=false` dùng `auto_campaign_actions.workflow_id`, `true` dùng `test_workflow_id`; khi bật test mà action thiếu `test_workflow_id` thì giữ campaign `'chờ xử lý'` với note, không fallback sang workflow thật.

Domain (sau migration_v4 drop engine v1):
- `auto_accounts` — tài khoản/social profile để login và chạy automation (trước đây là `org_accounts`); `proxy_id` nullable FK → `auto_proxies.id` để gắn proxy theo account; `rate_limit_minutes` là số phút khung check giới hạn giờ copy vào campaign khi lưu, default/fallback `65`, hiện không chỉnh ở UI account. Với Zalo QR (`is_zalo_show_web=false`), credential/session nằm trong `zalo_session` + timestamp/error fields; repository/list/preload chỉ trả `hasZaloSession` và identity an toàn, KHÔNG expose raw session. Với Zalo Web (`is_zalo_show_web=true`), cookie/bootstrap chỉ nằm trong Chromium partition local; DB chỉ giữ subtype, identity và login status công khai. Với Email, SMTP config nằm ở `email_session` + timestamp/error fields; tạo account bắt buộc verify SMTP, sửa metadata không verify lại nếu config không đổi. Với SMS, `username`/`password` là credential app mobile và `mobile_device_*` lưu thiết bị đang bind; UI account SMS ẩn status/login status nhưng hiển thị tên đăng nhập/mật khẩu và nút đổi điện thoại.
- `zalo_accounts` — shared identity catalog cho Zalo, dedupe toàn hệ thống bằng `zalo_uid UNIQUE`; lưu `display_name`, raw `phone`, `avatar_url`, metadata profile không-secret. Nhiều `auto_accounts` có thể trỏ cùng `zalo_account_id`; credential không được lưu ở bảng này.
- `zalo_users` / `zalo_groups` — meta danh bạ Zalo theo account, unique `(account_id, zalo_uid)` và `(account_id, zalo_group_id)` vì cùng một user/group Zalo có thể ra UID khác nhau theo tài khoản quét. Mỗi top-level field quan trọng từ `zca-js` có column riêng, object/array phức tạp giữ `jsonb`/`text[]`, `raw_payload` chỉ để audit; `zalo_groups.link` nullable dành cho cơ chế lấy link sau này, không được fetch thêm trong contact scan hiện tại.
- `zalo_group_members` — membership snapshot theo account/group/user, unique `(account_id, zalo_group_id, zalo_uid)`, FK tới `zalo_users`/`zalo_groups`, lưu role (`owner`/`admin`/`member`), `role_rank`, `is_current`, `raw_payload`, `last_seen_at`; re-scan group phải set `is_current=false` cho member không còn thấy. Member mirror vào `auto_account_contacts` dạng `person` theo `uid=zalo_uid` và giữ `is_friend=true` nếu trước đó đã là bạn bè.
- `auto_proxies` — kho proxy staff-scoped dùng chung cho nhiều account; hỗ trợ `http`/`https`/`socks5`, credential lưu DB và mask ở UI. Không cho xoá proxy đang được account dùng. Đổi proxy account hoặc sửa proxy chỉ update DB, không đụng runtime hiện tại nên được phép kể cả khi account/campaign đang chạy; proxy mới chỉ áp dụng khi session được prepare ở lần chạy/reload sau.
- `auto_status` — catalog trạng thái một bảng dùng cho UI/options; `code` là unique identifier để sau này có thể constraint/FK một cột (ví dụ `account_pending`, `campaign_pending`), các cột còn lại chỉ là metadata (`status_key`, `flatform_type`, `component_type`, default/terminal/manual flags). Hiện chỉ là lookup, chưa thay các cột text runtime như `auto_accounts.status`/`login_status` hoặc campaign status bằng FK.
- `auto_account_contacts` — danh bạ person/group/page theo account (trước đây là `org_account_contacts`); person dùng `is_friend` để lưu trạng thái bạn bè (`NULL` = chưa có API xác nhận), group dùng `is_joined` và `requires_post_approval` nullable để lưu trạng thái tham gia/duyệt bài. Tag akaBiz nội bộ gắn trực tiếp bằng `akabiz_tag_ids bigint[]`; một contact có thể có nhiều tag. Dữ liệu legacy `contact_type='friend'` chỉ đổi sang `person` qua script manual `migrations/manual_update_friend_contacts_to_person.sql`, không chạy tự động trong migration feature.
- `auto_contact_tags` — catalog tag akaBiz staff-scoped, soft delete bằng `is_delete`, unique active theo `(staff_id, lower(name))`; membership không dùng bảng join riêng mà lưu trong `auto_account_contacts.akabiz_tag_ids`.
- `auto_account_contact_groups` / `auto_account_contact_group_members` — `purpose='data_group'` là Data Group dùng chung theo staff/organization, không còn scope cứng theo account/contact type; membership dùng soft-delete + revision và mọi mutation/ingest phải đi qua [dataGroupRepository.ts](src/main/data/repositories/dataGroupRepository.ts) cùng RPC idempotent, tối đa 10.000 rows/request. `purpose='zalo_friend_blocklist'` vẫn account-scoped cho chiến dịch `zalo_message_friend`. Provenance bền vững của Data Group nằm ở `auto_account_contact_group_member_origins` / `auto_data_ingest_batches`; API mới nhận membership ID, không dùng contact ID để xoá/chuyển. Từ [migration v206](migrations/migration_v206_semantic_data_types.sql), semantic `common/data_type` được lưu theo group/dataset/origin/campaign input/action/automation, tuyệt đối không gắn cố định vào contact; group `NULL` hiển thị `Mọi loại dữ liệu` và là wildcard, còn group typed chỉ nhận origin cùng loại. [Migration v207](migrations/migration_v207_backfill_legacy_data_group_types.sql) chỉ backfill group legacy khi toàn bộ membership/current origin suy ra cùng một loại và source/automation còn tương thích. Dataset finalize/upload từ desktop phải gọi overload có `p_auth_username/p_auth_password`; overload chỉ có staff/org/account ID là service-role-only từ [migration v208](migrations/migration_v208_secure_dataset_writers_and_legacy_semantic_automation.sql). Panel thông tin từ [migration v240](migrations/migration_v240_data_group_info_panel.sql) phải tải một payload tenant-authenticated, bounded qua `aka_agent_get_data_group_panel`, không query trực tiếp các bảng support từ renderer; ghi chú tối đa 2.000 ký tự đi qua `aka_agent_update_data_group_note`. Popup campaign trong panel chỉ mở thẳng form sửa sau khi force-load config và xác nhận status còn `chờ xử lý|tạm dừng`; status khác chỉ báo lỗi, không mở detail dock. **Recovery**: desktop recovery staff-scoped chạy sau login, trước logout và trước app quit; không chạy global trước login. Login retry recovery tối đa 3 lần và không start automation nếu recovery thất bại. ContactLoader Facebook/Email phải claim/release account qua RPC atomic bằng `runtime_operation_claim_token`, không update status rời; release chỉ khôi phục claim còn đúng token. `recoverStuckCampaignInputData(campaignId, errMsg)` flip input_data stuck thành `'hoàn thành'` + `note=errMsg` khi outer catch (enum không có `'lỗi'`). `stop()` cũng đóng toàn bộ hidden background pages để không giữ tài nguyên nền.

**Schedule maintenance**: sau scoped recovery lúc login, `maintainCampaignSchedules()` ([campaignRepository.ts](src/main/data/repositories/campaignRepository.ts)) dọn campaign stale theo ngày `Asia/Ho_Chi_Minh`. Từ migration v223, mọi quyết định business theo giờ/ngày của Desktop và App Server phải lấy từ RPC `aka_agent_get_runtime_clock()`, không dùng wall clock máy/VPS làm fallback. [runtimeClockRepository.ts](src/main/data/repositories/runtimeClockRepository.ts) giữ DB epoch rồi tiến thời gian bằng `performance.now()`, lazy resync tối đa mỗi 10 phút, bắt buộc resync tại 0h Việt Nam và Desktop invalidate khi suspend/resume. `DailyMaintenanceCoordinator.ensureReady()` là barrier trước discovery/claim: sang ngày mới phải maintenance thành công rồi scheduler mới nhận campaign; lỗi clock/maintenance phải fail-closed và tự thử lại. Từ [migration_v231_campaign_daily_runtime_boundary.sql](migrations/migration_v231_campaign_daily_runtime_boundary.sql), Desktop và Zalo Server dùng top-level runtime claim có UUID/date bất biến rồi claim durable `runtime_unit_*` trước từng target/batch; cutoff là inclusive theo DB clock tại `min(daily_stop_time, 23:59)`, `daily_stop_time=NULL` vẫn bắt buộc dừng nhận lượt mới lúc 23:59. Unit đã claim trước cutoff được chạy và ghi xong kể cả qua 0h, nhưng maintenance DB barrier phải chờ lease cũ settle/recovery rồi mới chạy; tuyệt đối không dùng host-clock/non-atomic fallback hoặc clear lease bằng status write. Startup luôn recovery unit lease trước maintenance, còn same-day rerun (`findDataRerunEnabled`) phải so lịch kế tiếp với `claimedVietnamDateKey` để lượt 23:58→00:02 không tự hẹn sang ngày mới trước maintenance. Slot 23:59 bị UI từ chối cho campaign Desktop/Server; SMS/voice mobile-managed không thuộc runtime boundary này. Daily quota create/read/reset dùng RPC atomic `aka_agent_get_account_action_status_today(...)`; giữ `SECURITY INVOKER` và quyền runtime roles khi thay RPC. Daily/weekly/monthly dùng giờ từ `original_schedule ?? schedule` để tính lịch mới; automation chỉ update runtime `schedule`, còn user tạo/sửa campaign mới update cả `schedule` và `original_schedule`. Khi maintenance thực sự dời lịch daily/weekly/monthly sang kỳ mới thì phải xóa `note` cũ cùng update đó; các tick maintenance sau không chạm lại campaign khi lịch đã ở đúng kỳ. Với daily còn `'chờ xử lý'`, `continueNextDay=true` nghĩa là qua ngày sẽ dời runtime `schedule` sang giờ hẹn của ngày mới; `continueNextDay=false` giữ nguyên runtime `schedule` cũ để nó tiếp tục ở trạng thái đã tới giờ ngay sau nửa đêm, không tự ý đổi giờ user thành 00:00. Checkbox này chỉ điều khiển có chờ giờ hẹn ngày mới hay không, không quyết định "có chạy tiếp hay không"; campaign đã `'hoàn thành'` không tự bật lại. Weekly/monthly `refreshData=true` reset `auto_campaign_input_data` rồi bật lại `chờ xử lý`; completed no-refresh chỉ update `schedule`. Hard-end Data Group dựa trên ngày kết thúc và chỉ sweep một lần trong daily maintenance sau khi barrier mở, không quét mỗi scheduler tick.

**Desktop campaign resume**: từ [migration_v234_queue_desktop_campaign_while_account_running.sql](migrations/migration_v234_queue_desktop_campaign_while_account_running.sql), resume chỉ chuyển campaign `'tạm dừng'` sang `'chờ xử lý'` dù account đang `'đang chạy'` bởi campaign/tác vụ khác; scheduler và RPC claim runtime chịu trách nhiệm serialize theo account. Vẫn phải từ chối resume khi chính campaign còn runtime claim hoặc unit lease chưa giải phóng.

**Rate limit** ([campaignRepository.ts:getAccountRateLimitStatus](src/main/data/repositories/campaignRepository.ts)) dùng `action_code`:
- Daily limit so với `auto_account_action_status.count_action_in_day` (reset 00:00 Asia/Saigon).
- Hourly/window limit query `auto_campaign_details` theo `(account_id, action_code, created_at)` và đếm `counts_toward_limit=true` hoặc `counts_toward_limit IS NULL AND status IN ('thành công','thất bại')`; đừng default cột này thành `true` vì sẽ đổi nghĩa legacy/Facebook.
- Scheduler phải peek quota/disable read-only trước claim để campaign đang bị giới hạn không chuyển sang `'đang chạy'`; peek không được tạo/reset/lock row quota. Nếu DB vẫn blocked và campaign đã có đúng note preflight hiện tại thì bỏ qua mọi write/claim; note mới hoặc thay đổi được ghi bằng CAS chỉ khi campaign vẫn `'chờ xử lý'`, đúng `updated_at` đã đọc và chưa có runtime claim/unit token, tuyệt đối không claim account chỉ để ghi note. CAS thua phải reload/broadcast row thắng mà không ghi đè hoặc release owner mới. `claim_campaign_runtime` xóa note khi claim thành công, còn kiểm tra quota authoritative sau claim/per-target vẫn phải giữ để xử lý race.
- ActionManagerModal stores candidate quota checks in `auto_campaign_actions.limit_check_action_codes`; Campaign form auto-saves visible quota checks to `extra_settings.actionLimits.enabledActionCodes` for scheduler compatibility. `enabledActionCodes` only controls daily/window quota checks; scheduler must still enforce `auto_account_action_status.is_disable` for every executable action even when that action code is absent from `enabledActionCodes`.
- Campaign form stores thresholds in `extra_settings.actionLimits.byActionCode[action_code]`; `rateLimitMinutes` is copied from `auto_accounts.rate_limit_minutes` per account when saving, fallback `65`; scheduler also filters out checks for campaign actions disabled by toggles such as `enableAddFriend=false`.
- `extra_settings.actionLimits.continueWhenActionLimitReached=true` means hourly/daily quota hits can skip only that action and keep running remaining quota actions; missing/false keeps fail-fast behavior. This does not apply to action disable/error policy (`is_disable`), which always stops. Scheduler maps skipped `fb_comment`/`fb_like_post`/message/add-friend quota to workflow vars (`enableComment=false`, `enablePostLike=false`, `enableMessage=false`, `enableAddFriend=false`). For `zalo_message_phone`, `zalo_find_phone_user` is a dependency, not a continuable business action; if both selected `zalo_message_stranger` and `zalo_add_friend` are quota-limited, campaign waits even when find-phone quota remains.
- Limit notes/logs must include the exact action name; `auto_error` messages may use `[a]`/`[action]` and `[action_code]` placeholders.
- Khi hit limit/disable action: campaign về `'chờ xử lý'`, ghi `note`; KHÔNG đổi schedule.
- `facebook_group_invite` runs targets as one dialog batch and only decrements `fb_group_invite` quota after checked targets submit successfully; already invited/already member/not found statuses are skipped outcomes, not bad-target errors. Form-open/runtime errors pause the campaign because they likely mean Facebook DOM changed. Submit errors pause the campaign, keep already-invited/already-member/not-found details, and reset checked targets to `chờ xử lý` without creating error details.

Nếu không còn entitlement nào, main process cleanup rồi emit `AUTH_SESSION_EXPIRED`. RLS policy `org_organization_product_read_all` cho anon/authenticated SELECT bảng này để app desktop tự kiểm tra; không mở quyền ghi. Login UI phải hiển thị lỗi nghiệp vụ thân thiện và lọc prefix IPC/PostgREST/schema cache, không show log kỹ thuật cho user. Đổi mật khẩu dùng `AUTH_CHANGE_PASSWORD`, kiểm tra mật khẩu cũ rồi update `org_staff.password`; `AuthUser.isAdminAkabiz` lấy từ `org_staff.is_admin_akabiz`, không dùng `staffId === 1`; `AuthUser.useTestWorkflow` lấy/lưu từ `org_staff.use_test_workflow`.
- Trong [authProductCatalog.ts](src/shared/authProductCatalog.ts), `AUTH_PRODUCT_CATALOG` giữ danh mục row vật lý/legacy theo từng Product ID, còn `AUTH_PRODUCTS_BY_FEATURE` là lookup quyền hiệu lực: cả `facebookCore` và `facebookFanpage` đều phải trả Product `[3,10]`. `AUTH_PRODUCT_BY_FEATURE` singular chỉ dành cho Email/SMS; không dùng singular lookup cho Facebook hoặc Zalo.
- Account creation quota dùng `org_organization_product.max_accounts` snapshot vào `AuthUser.entitlements.accountLimits` và hiển thị trong `AuthUser.accountProducts.maxAccounts`; chỉ chặn ở backend khi bấm tạo/đổi platform account. Facebook dùng quota chung từ tất cả row Product 3/10 còn hạn; Zalo dùng một quota chung QR + Web + Server từ tất cả row Product 16/18 còn hạn. Mọi account Zalo `is_delete=false` của staff đều tính slot kể cả inactive hoặc subtype đang bị ẩn/mất capability. Với các platform khác quota tính theo `staff_id + flatform_type + is_delete=false`; `max_accounts` rỗng/không hợp lệ nghĩa là không giới hạn.
- Khi gộp Facebook Product 3/10 hoặc Zalo Product 16/18, `không giới hạn` lớn hơn mọi giới hạn hữu hạn: chỉ cần một row còn hạn có `max_accounts` rỗng/không hợp lệ thì quota account chung là không giới hạn. Với `max_sends_per_day`, mỗi row demo rỗng dùng mặc định 30, còn row paid rỗng là không giới hạn; nếu một row đã resolve thành không giới hạn thì quota gửi chung cũng không giới hạn.
- `AuthUser.accountProducts` gộp mọi row Facebook Product 3/10 còn hạn thành một card `Facebook` và mọi row Zalo Product 16/18 còn hạn thành một card `Zalo`: `maxAccounts` lấy quota chung và ngày hết hạn hiển thị là ngày xa nhất. Các row Facebook đã hết hạn vẫn giữ riêng để xem lịch sử; Zalo không còn row hợp lệ thì giữ một card hết hạn mới nhất như hành vi cũ.
- Akachat customer ingestion lives in Supabase Edge Functions: [insert_aka_customer](supabase/functions/insert_aka_customer/index.ts) resolves owner by existing owner → `staff_id`/`chat_staff_id` → `aka_data_split_rules`, then calls [create-aka-crm](supabase/functions/create-aka-crm/index.ts). Migration [migration_v71_akachat_customer_crm_split.sql](migrations/migration_v71_akachat_customer_crm_split.sql) creates split rules and disables the old `trg_aka_customer_split_create_crm` trigger.

Migration pattern: write SQL files under `migrations/` (`migrations/migration.sql` for base schema, keep versioned files as `migrations/migration_vN_*.sql`, e.g. `migrations/migration_v2_workflow.sql`, `migrations/migration_v3_campaign_data.sql`, `migrations/migration_v6_rename_campaign_workflow_tables.sql`, `migrations/migration_v34_message_uid_campaign.sql`). Apply via `mcp__supabase__apply_migration`. Use idempotent UPSERT by UNIQUE name for engine v2 or explicit IDs where appropriate.

### Vietnamese UI conventions

Status values trong DB lưu **tiếng Việt có dấu**:
- Campaign: `'chờ xử lý'`, `'đang chạy'`, `'hoàn thành'`, `'tạm dừng'` (KHÔNG có `'lỗi'` trong runtime hiện tại)
- campaign_inputs: `'chờ xử lý'`, `'đang chạy'`, `'hoàn thành'`, `'lỗi'`, `'tạm dừng'`
- campaign_input_data: `'chờ xử lý'`, `'đang chạy'`, `'hoàn thành'`, `'tạm dừng'` (KHÔNG có `'lỗi'`)
- campaign_details: `'thành công'`, `'thất bại'`, `'lỗi'`
- automation_detail: `'chờ xử lý'`, `'đang xử lý'`, `'đã thêm'`, `'bỏ qua'`, `'lỗi'`
- Login status: `'đã đăng nhập'`, `'chưa đăng nhập'`, `'checkpoint'`

**Customer-facing log language** (rất quan trọng — log từ `sendLog()` và `auto_campaign_details.log` đều khách hàng đọc):
- Viết tiếng Việt tự nhiên: `"Đã comment vào bài thứ 3: ..."`, `"Đăng bài thành công vào ..."`, `"Group cần duyệt bài"`
- TRÁNH: `"Đã log X"`, `"lần X/Y"`, `"vị trí #N"`, ID strings, stacktraces, `"position"`, `"iteration"`, `"campaign_detail"` lộ ra UI
- Technical metadata (`commentPosition`, `iteration`, `commentType`) → JSONB `data` column, KHÔNG vào `log` string
- Progress log theo campaign dùng `CampaignScheduler.logCampaignProgress()` để vừa append vào `auto_campaigns.log`, vừa bắn panel phải "Tiến trình", vừa broadcast campaign updated; UI đọc `auto_campaigns.log` ở tab "Lịch sử chạy".
- `auto_campaigns.log` phải format qua [campaignLogFormat.ts](src/shared/campaignLogFormat.ts): stored line `HH:mm:ss dd/MM/yyyy - account - campaign - message`, giữ emoji/marker screenshot, reader dùng `parseCampaignLogLine()` để hỗ trợ cả log cũ dạng `[timestamp] message`.
- Screenshot progress log là artifact-only (`📸 Ảnh chụp màn hình trạng thái trình duyệt`), ghi sau log kết quả action khi match được step, có thể kèm action realtime `block_screenshot_preview` để nút `Xem` mở ảnh trong app; raw `auto_campaigns.log` được thêm marker ẩn `<!-- screenshotEventId:N -->` để match event, UI phải strip marker và không được lưu local file path vào log text.
- Khi campaign chạm ngưỡng lỗi liên tiếp, log `⚠️ Chiến dịch đã lỗi/thất bại liên tiếp...` dùng root cause từ `auto_campaign_details.data.error`; riêng `err_undefined` có screenshot thì AI diagnosis có thể thay root cause, nhưng không được đổi policy/counter/status.
- Với workflow Zalo, `zalo_tag_contact` và `zalo_change_alias` là action phụ: kết quả vẫn ghi `auto_campaign_details` theo `detail_status` nhưng thành công/thất bại đều không tăng hoặc reset bộ đếm bad-target liên tiếp. Action chính/tiên quyết như tìm SĐT, nhắn tin, kết bạn, thao tác group vẫn bám `auto_error.counts_toward_bad_target`; mọi side effect explicit của policy (`update_status_*`, `disable_action_codes`, `update_login_status`) vẫn phải thực thi kể cả khi lỗi phát sinh ở action phụ.
- Email recipient precheck chỉ ghi log khách hàng ngắn như `Email không tồn tại user@example.com`; không đưa raw SMTP reason (`550-5.1.1...`), DNS/debug text, stacktrace hoặc URL support vào `auto_campaign_details.log`. Metadata kỹ thuật nếu cần thì để trong JSONB `data.recipientCheck`.
- Scheduler/global `sendLog()` lỗi mất mạng phải dùng câu thân thiện, không lộ `TypeError: fetch failed`; chỉ log một lần cho mỗi đợt mất kết nối, giữ lỗi kỹ thuật trong `console.error`, và chỉ log kết nối lại sau khi toàn bộ tick scheduler chạy xong không lỗi.
- **Log order**: action milestone trước (📝 Đăng bài), rồi metadata (⏳ Chờ duyệt), rồi link/artifact (🔗), milestones tiếp theo (💬), cuối cùng summary (✅/❌)
- Emoji vocab thống nhất: 📝 Đăng bài • 💬 Comment/Nhắn tin • 🔗 Link • ⏳ Chờ duyệt • ✅ Hoàn thành • ❌ Lỗi • 👋 Rời nhóm • 🤝 Kết bạn/Tham gia • 🔀 Shuffle/Share • ⚠️ Cảnh báo • ℹ️ Info • 🎬 Reels

**Per-milestone logging**: post xong ghi 1 row, mỗi comment ghi 1 row, friend request ghi 1 row — KHÔNG đợi cuối flow. Lý do: nếu comment failed sau khi post OK, vẫn phải có row "Đăng bài thành công" để khách hàng thấy. Với `fb_comment_at_position`, lỗi ở một bài trả `commentFailed=true`/detail `thất bại` và loop vẫn tiếp tục bài sau; chỉ khi không có milestone thành công nào thì target comment seeding mới bị tính bad.

## Common pitfalls

- **Migration RPC overwrite**: trước khi dùng `CREATE OR REPLACE FUNCTION`, phải lấy nội dung của đúng function signature đang chạy trong DB (ví dụ bằng `pg_get_functiondef`) và kiểm tra các patch trước đó; không copy body từ một migration cũ vì có thể làm mất những thay đổi được áp dụng sau migration đó.
- **Error action-disable policy**: không hard-code thời gian nghỉ theo từng `error_code` trong scheduler. Thêm lỗi tương tự bằng row `auto_error` với `disable_action_codes` + `disable_action_mode`; bỏ mode sẽ fallback `fixed_minutes`, và `fixed_minutes` thiếu số phút sẽ khóa action vô thời hạn.
- **Account restriction summary**: danh sách tài khoản phải lấy một batch `auto_account_action_status` trong `listAccounts()` để dựng `hasDisabledActions`, không gọi `ACCOUNT_ACTION_OVERVIEW` N+1 theo từng card; row `date_enable` đã hết hạn không được tô tím. Sau khi scheduler khóa action phải broadcast `ACCOUNT_STATUS_UPDATED` để renderer refresh cờ này.
- **App notification bar**: không tạo `auto_app_notifications`; chỉ dùng `auto_system_settings.app.notification`. Poll interval 60 phút không có nghĩa thay đổi DB luôn chờ 60 phút vì focus/visibility vẫn refresh ngay. Cảnh báo offline là state local ưu tiên cao hơn DB và phải tự khôi phục notification DB khi event `online` chạy.
- **Loop iterations**: scheduler `logMilestonesV2` đọc `result.steps` từ engine. Engine v2 maintain `allSteps[]` (mỗi loop iteration 1 row riêng) thay vì snapshot `nodeStates`. Khi đọc per-iteration data, đọc `s.output` (block return value), KHÔNG `s.input` (chỉ là config + parents trực tiếp).
- **Skipped action steps**: `logMilestonesV2` must ignore `status='skipped'` action blocks. Optional workflow branches (e.g. `enableAddFriend=false`) still return snapshot steps, but they are not real user actions.
- **Page Inbox composer settle**: `fb_send_page_inbox_message` phải giữ delay `facebookStepMs + 4000ms` sau khi clear search và trước khi đọc header/tìm ô nhập; Business Inbox render composer trễ nên fixed `2000ms` gây lỗi giả `Không tìm thấy ô để nhập tin nhắn` ([migration_v211_facebook_page_inbox_message_input_settle_delay.sql](migrations/migration_v211_facebook_page_inbox_message_input_settle_delay.sql)).
- **Newsfeed interaction**: `fb_newsfeed_*` blocks should skip unreadable/non-actionable posts instead of failing the whole run; only `liked === true` / `commented === true` action outputs should create `auto_campaign_details` rows. `enablePostLike`/`enableComment`, not kind text, gate runtime/quota; partial quota and pause abort must stay gated to `facebook_newsfeed_interaction`. Keep newsfeed action selectors scoped to the current `postEle`; `findActionRoot`/ancestor normalization can include comment DOM and click/comment the wrong target.
- **Comment seeding keyword miss**: `fb_prepare_seeding_iterations` có thể trả `commentIterations=[]`; loop body chỉ chạy bên trong loop executor, keyword/text phải normalize bỏ dấu + whitespace, và text bài phải lấy bằng `fb_post_in_uid` + `fb_content_in_post_in_uid` thay vì raw `[role=article]` ([migration_v14_comment_seeding_find_data_content.sql](migrations/migration_v14_comment_seeding_find_data_content.sql)).
- **Comment media-only logs**: `fb_comment_at_position` có thể return `text=''` nhưng legacy field `imageCount>0` cho cả ảnh/video; `logMilestonesV2()` vẫn phải tạo row Comment, không skip theo text rỗng ([campaignScheduler.ts](src/main/services/campaignScheduler.ts), [migration_v18_comment_images.sql](migrations/migration_v18_comment_images.sql)).
- **Output cascade**: engine v2 KHÔNG có inputMapping — output của parent merge vào input của child theo edges, last-write-wins. Output `scrapedText` của block ở xa KHÔNG cascade qua chain — nếu cần dùng ở downstream chain dài, **mutate `vars`** thay vì rely on input merging.
- **XPath union `|`**: timeline page và group page dùng selector khác nhau. Element store XPath với `|` để match cả hai. `document.evaluate` (XPath 1.0) hỗ trợ union, trả node đầu tiên match.
- **Optional Facebook composer Next**: `fb_click_post_button` là block dùng chung cho timeline/group. Không dùng `waitForSelector` dài hoặc để lỗi `FbComposerNextButton` làm fail block; probe bằng `page.$`, nuốt lỗi lookup/click, chỉ chờ 2 giây khi click thành công rồi mới chạy bước Post/Đăng bắt buộc.
- **`auto_runs.workflow_id` column**: tên cột là `workflow_id` nhưng FK → `auto_workflows.id` (BIGINT). Đừng nhầm với cột `workflow_id` (UUID) đã drop ở migration_v4 thuộc `auto_campaign_actions`.
- **Automation claim conflict target**: `claim_auto_automation_details` là `RETURNS TABLE`, nên output `target_campaign_id` cũng là biến PL/pgSQL; giữ `ON CONFLICT ON CONSTRAINT auto_automation_target_counters_pkey` từ [migration v175](migrations/migration_v175_automation_claim_conflict_hotfix.sql), không đổi lại thành `ON CONFLICT (target_campaign_id)` vì sẽ ambiguous lúc runtime.
- **timeSleepBetween2** vs **actionLimits.sleepBetweenActions**: scheduler ưu tiên `actionLimits.sleepBetweenActions`, fallback `campaign.timeSleepBetween2`. Cả 2 tính bằng giây; `0` là giá trị hợp lệ cho campaign up tin nên scheduler/repository phải dùng `??`, không dùng `||`.
- **Schedule edit** (`scheduleEndDate`): cột nullable, type `string | null | undefined`. Pass `null` (không phải `undefined`) để clear — `updateCampaign`'s `!== undefined` check sẽ skip undefined. Cho `scheduleType='daily'`, luôn gửi `null` (form date input disabled nhưng formData vẫn giữ default 7-day-ahead, sẽ silently stop campaign sau 1 tuần).
- **Creating campaigns with input data**: campaign form must create new campaigns in temporary `tạm dừng`, insert all `auto_campaign_input_data`, finish any draft/find-data link patching, then resume to the intended final status. Never expose a new data-backed campaign as `chờ xử lý` before its input rows and internal source/target links are complete.
- **Group template snapshots**: chọn dropdown chỉ là candidate; chỉ `Dùng nhóm này` tạo pending và chỉ save campaign mới đọc lại/flatten/persist. Riêng `sms_send` tối đa 100 item sau flatten; đây không phải giới hạn người nhận, không được truncate, và Zalo/Facebook/Email không có cap 100. Runtime và refresh-failure path phải giữ snapshot cũ, không lookup nhóm/mẫu hoặc fallback Base/generic channel ([contentTemplateCampaignUtils.ts](src/renderer/src/components/CampaignPanels/contentTemplateCampaignUtils.ts), [campaignScheduler.ts](src/main/services/campaignScheduler.ts)).
- **Hidden vs disabled toggle** (`sharePost` pattern): feature có DB flag nhưng chưa implement → ẨN khỏi UI (don't render checkbox), giữ flag trong `formData` + `handleSave` payload (preserve roundtrip), backend log warning per run. KHÔNG `<input disabled>` (leak feature name).
- **Minimized campaign runs**: scheduler chạy campaign bằng hidden/offscreen `BackgroundPageManager`; visible webview có thể không paint khi minimized/hidden nên chỉ dùng cho login/test/manual. BrowserPage quan sát qua preview stream.
- **Zalo routing is per account**: QR local (`false,false`) và Server (`false,true`) đều browserless; chỉ `auto_accounts.is_zalo_show_web=true,is_zalo_server=false` được mount trong BrowserPage/WebviewRegistry với partition `persist:account_<id>`. Login/check/logout/scan/campaign và renderer operation state phải đọc subtype account; không route theo legacy `AuthUser.isZaloShowWeb`/`AuthUser.isZaloServer`.
- **Email recipient precheck must stay conservative**: only return `not_found` for invalid format, no MX/A or Null MX, or clear SMTP recipient-not-found responses. Network blocks, SMTP timeouts, greylisting, sender/auth rejection, or ambiguous 5xx responses must be `unknown` so the normal SMTP send still runs.

UI/backend guards use the refreshed `AuthUser.entitlements` and `zaloAccountCapabilities`; do not add ad-hoc `org_organization_product` queries to scheduler/account poller/realtime managers/list repositories. Admin campaign action management is configuration and should not filter out Email.
- **Zalo API-only campaigns**: `zalo_message_phone`, `zalo_message_friend`, `zalo_message_group`, `zalo_message_birthday`, `zalo_message_group_member`, `zalo_message_group_realtime`, `zalo_message_remarketing_customer`, `zalo_message_friend_recommendation`, `zalo_add_group_member`, and `zalo_join_group_link` run workflow v2 with `page=null`; helpers must call `ZaloRuntimeService.ensureApi(accountId)`, which routes by the account subtype. Scheduler verifies login with `checkSession()` before marking campaign running and logs raw failures to `zalo_api_error_logs`. A Web account still requires its visible tab/partition to be registered, but campaign execution must not create a second browser/profile. `zalo_add_group_member` imports phone-only data; UID targets must come from account-scoped Zalo scan data.

Phân loại `fixed_minutes` là giới hạn giờ, `end_of_day` là giới hạn ngày và ưu tiên lỗi giờ khi cả hai bucket bị chặn; không gọi thẳng `zca-js api.findUser()` vì bản hiện tại hard-code `reqSrc=40`.
- **Zalo error policy/action retry**: `auto_error.zalo_action_codes` rỗng là policy global; mọi lookup raw `zalo_error_codes` phải truyền action phát sinh để cùng mã Zalo không disable nhầm action. Sau khi helper trả `deliveryCommitted=true`, lỗi/pause/account-stop phía sau không được đưa input về `chờ xử lý` ([errorPolicyRepository.ts](src/main/data/repositories/errorPolicyRepository.ts), [campaignScheduler.ts](src/main/services/campaignScheduler.ts)).
- **Zalo join group by link**: input data stores the group link in `auto_campaign_input_data.uid`; accept and normalize `zalo.me/g/...` and `zaloapp.com/qr/g/...` to `https://zalo.me/g/...` in upload/runtime. `joinGroupLink` code 178 creates detail status `đã tham gia` with `counts_toward_limit=false` and no `error_code`; code 240 is `thành công`, counts quota, and mirrors group contact with `is_joined=false`.
- **Zalo group theo thời gian thực**: listener lifecycle stays in `ZaloRuntimeService`; [zaloRealtimeGroupCampaignManager.ts](src/main/services/zaloRealtimeGroupCampaignManager.ts) only routes `group_event`/`message`/`reaction` into campaign data. Received/duplicate data logs go to `auto_campaigns.log` ("Lịch sử chạy"), not `auto_campaign_details` ("Kết quả chạy") and not the progress panel.
- **Zalo campaign user upsert**: user-target Zalo campaigns may upsert `zalo_users` + `auto_account_contacts.person`, but only from metadata actually returned by Zalo API (`findUserByPhone`, `getAllFriendsPage`, `getUserProfile`). Do not populate contact metadata from `auto_campaign_input_data`; do not set `is_friend=false` unless API returns an explicit `isFr`/friend status. `zalo_message_group` does not upsert groups or fetch extra group metadata.
- **Zalo share message mode**: friend/group campaign option `extraSettings.zaloMessageSendMode='share'` bypasses workflow execution after scheduler preflight and sends text via raw Zalo `/api/message/mforward` or `/api/group/mforward` in batches up to 50. Do not use `zca-js api.forwardMessage` for campaign share mode because it reuses one `clientId` for the whole batch; build per-target `clientId` values and map success/fail by `clientId` (or target id when Zalo returns one). Skip own UID before sending friend share batches so one self target does not make Zalo reject the entire batch with `114`.
- **Zalo friend "Danh sách không gửi tin"**: `zalo_message_friend` can enable `extraSettings.zaloFriendBlocklistEnabled` with a contact group `purpose='zalo_friend_blocklist'` scoped to the same account. Scheduler loads UID snapshot once, checks before quota/workflow/API/share batch, marks skipped input data `hoàn thành` with note/date, does not create `auto_campaign_details`, and does not count quota. Normal mode logs each skipped target in progress; share mode logs only the total skipped count.
- **Zalo remarketing customer picker**: `zalo_message_remarketing_customer` selects targets from previous Zalo message `auto_campaign_details`, but detail JSON is only history/fallback. Resolve display data from `auto_campaign_input_data`, `zalo_users`, `auto_account_contacts`, `zalo_group_members`, and `zalo_groups`; friend status must come from `auto_account_contacts.is_friend` or `zalo_users.is_fr`, not `data.target.isFriend`.
- **Zalo auto-materialized input data**: `zalo_message_friend` modes `all_friends`/`tagged_friends` materialize friend rows only once per campaign and clone must not copy those rows or materialized markers. `zalo_message_friend_recommendation` calls `getFriendRecommendations()` once per campaign/account at runtime, materializes UID/name/phone only into `auto_campaign_input_data`, marks empty results as completed, and upserts contacts only later when resolving each UID. `zalo_message_birthday` materializes by run date from `getAllFriendsPage(...).sdob.slice(0, 5) === dd/mm`; daily is one-shot, while weekly/monthly soft-delete old birthday input rows and clear birthday materialized metadata before the next occurrence.
- **Zalo contact scan is API-only**: friend/group/group-member data scans must go through `ZaloRuntimeService`; do not create webviews/browser profiles and do not call extra link APIs during group scan. `ContactLoader` friend scan delays randomly 2–5 seconds after `checkSession()` and between 500-row `getAllFriends` pages; HTTP 429 from session/page calls is transient and retries after 15/30/60 seconds while still honoring scan cancellation. Friend/group scans may call `getLabels()` once to sync Zalo label catalog (`contact_type='zalo_tag'`) and mirror tag membership from `label.conversations` into `auto_account_contacts.extra_data.zaloTagIds`/`zaloTagNames`/`zaloTags`; do not backfill Zalo tags from old `auto_campaign_details`. `DataScanModal` should keep Facebook table columns stable; Zalo-only avatar/phone/tag columns are gated by platform, while Zalo group `Link` displays the stored nullable `auto_account_contacts.url`. DataScan Zalo tag/akaBiz tag filters are query state sent through shared list query types and main repositories (not renderer-only UI filters); keep multi-select OR within each tag filter, AND between Zalo tag and akaBiz tag filters, and preserve the `Chưa gắn tag` flags. Group-member link mode may decode QR payloads like `zaloapp.com/qr/g/...` but must normalize them to `https://zalo.me/g/...` before calling runtime.
- **DataScan pagination/selection**: non-Page-Inbox data tables use backend pagination/search/export through account contact, Zalo group member, or Zalo remarketing list APIs; default page size is 100. Header checkbox selects all matching backend filters across pages, tracks exclusions, and export/add-to-campaign/create-group must fetch the backend selection instead of only current page rows. - **Async renderer mutation locks**: nút Lưu/Thêm/Xác nhận phải bật trạng thái busy trước `await` đầu tiên và disable trigger trong suốt mutation. Nếu handler có pre-work async hoặc mutation không idempotent, dùng thêm `useRef` mutex đồng bộ để nhiều click trước lần render kế tiếp vẫn chỉ tạo một request; modal không được đóng/chuyển action trong lúc request đang chạy.

- **Zalo session single-use/race**: one Zalo session should not be logged in concurrently by multiple API instances for the same `auto_account`. `ZaloRuntimeService` serializes login through `apiLoginInflight` and serializes verify/retry through `verifyInflight`; keep new Zalo tasks behind `ensureApi(accountId)` and avoid direct `zalo.login(session)` calls.
- **Zalo credential exposure**: `auto_accounts.zalo_session` is secret runtime credential. Account list mappers/preload/UI must not return raw cookies/session to renderer; only main process Zalo runtime/repository methods may read/write it.
- **Minimized data scans**: `ContactLoader` cũng chạy bằng hidden/offscreen `BackgroundPageManager` + workflow v2 built-in. Không đưa logic scrape mới về visible webview; nếu cần đổi selector/logic quét thì seed/update `auto_blocks`/`auto_workflows` bằng migration.
- **Post-scoped contact filters**: khi thêm nguồn quét theo post, luôn lưu và merge `extra_data.sourcePostRefs` theo cặp `{ source, url }`, đồng thời truyền `AccountContactListQuery.source` trong UI list/export/select. Comment workflows support exactly 1 image/video per comment: `commentImageOption='all'` chỉ hợp lệ với tối đa một media, còn `random` giữ một pool và scheduler resolve đúng một media cho từng lượt; `fb_comment_at_position` drops into the dialog textbox after clicking the indexed comment box. Sau `dropFile()` trả về, cả `fb_comment_at_position` và `fb_comment_current_post` phải giữ settle delay 10.000ms trước submit; đây là fixed safety delay, không phải tín hiệu DOM xác nhận upload xong ([migration_v234](migrations/migration_v234_facebook_comment_media_settle_delay.sql)).
