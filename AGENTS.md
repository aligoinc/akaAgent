## Architecture

**Electron 33 + React 19 desktop app** cho automation Facebook/Zalo/Email. Build qua `electron-vite`. State Zustand. Canvas `@xyflow/react`. DB Supabase. Code editor Monaco.

### 3-layer Electron split (`src/`)

| Layer | Path | Trách nhiệm |
|---|---|---|
| Main process (Node) | [src/main](src/main) | IPC, DB (Supabase), webview controller, scheduler, updater |
| Preload bridge | [src/preload/index.ts](src/preload/index.ts) | Expose `electronAPI.*` qua `contextBridge` |
| Renderer (React) | [src/renderer/src](src/renderer/src) | UI, Zustand stores, xyflow canvas, Monaco editor |
| Shared | [src/shared](src/shared) | Types + IPC event constants (cả 2 phía import) |

### Webview controller

[src/main/playwright/webviewController.ts](src/main/playwright/webviewController.ts) — thin wrapper exposing `isConnected()` + `getURL()` cho `webContents` của Electron `<webview>` đã embed cho từng tài khoản FB. Visible webviews vẫn dùng cho login, status checks và test thủ công trong editor.

`WebviewRegistry` maps `accountId -> webContentsId`. Scheduler uses `isRegistered()` to ensure the account has mounted a browser tab at least once; accountPoller uses `listRegistered()` to skip dead tabs. Runtime uses `accountId` and partition `persist:account_${accountId}`; browser profiles from the previous partition prefix are not reused. For browser-based accounts, account proxy is prepared by `ProxyRuntimeService` on this same partition before background page loads and when user manually reloads visible webview; editing/assigning proxy only saves DB and must not auto-reload, close connections, or destroy visible/background pages. Account context actions "Hiển thị & xem trang web" and "Load lại trang web" must ensure BrowserPage opens/mounts the visible webview when `WebviewRegistry` has no tab yet; do not surface "Tab trình duyệt chưa được mở" for these user-triggered open/reload actions.
Zalo phase hiện tại là API-only qua [zaloRuntimeService.ts](src/main/services/zaloRuntimeService.ts) + `zca-js`: không tạo tab/webview, không prepare browser session, không tạo partition/profile browser, và [BrowserPage.tsx](src/renderer/src/pages/BrowserPage.tsx) phải filter `BROWSERLESS_PLATFORMS`. Zalo session/cache sống trong main process; mọi feature Zalo mới phải lấy API qua `ZaloRuntimeService.ensureApi(accountId)` thay vì tự login hoặc đọc cache trực tiếp. Zalo group theo thời gian thực dùng [zaloRealtimeGroupCampaignManager.ts](src/main/services/zaloRealtimeGroupCampaignManager.ts) subscribe listener do `ZaloRuntimeService` sở hữu; manager không tự login/stop API và không backfill event bị lỡ khi offline/logout. Email cũng là browserless: SMTP gửi bằng [emailRuntimeService.ts](src/main/services/emailRuntimeService.ts) + `nodemailer`, không mount webview/tab, không prepare browser session, và dùng cùng filter `BROWSERLESS_PLATFORMS`.
Zalo QR login trong AccountPanel dùng modal renderer + `ZaloRuntimeService.startLoginQr(accountId)`: tạo mới account Zalo phải tự mở QR ngay sau khi account DB đã tạo; QR hết hạn không auto-retry, không rollback/xoá account, modal giữ mở với nút "Đăng nhập lại" để user chủ động tạo QR mới. Khi user đã quét QR, ô QR hiển thị avatar + tên Zalo, message dưới chỉ là note xác nhận.
ContactLoader là utility ngoài campaign nhưng chạy bằng workflow v2 built-in trên hidden/offscreen `BackgroundPageManager`, output lưu vào `auto_account_contacts`; riêng Page inbox `contact_type='page_inbox_customer'` lưu SQLite local qua [localAccountContactRepository.ts](src/main/data/repositories/localAccountContactRepository.ts) tại `app.getPath('userData')/local-data/aka_agent_local.db`. Chỉ load khi account `isActive=true`, `loginStatus='đã đăng nhập'`, `status IN ('chờ xử lý','tạm dừng')`. Khi quét, account được set `status='đang chạy'` để scheduler không chạy campaign đè cùng session; account đang `'đang chạy'` thì không cho quét. Facebook user lưu `contact_type='person'` + `is_friend=true` khi quét danh sách bạn bè; nếu lần quét sau không còn thấy thì set `is_friend=false` và giữ `is_delete=false`. Group còn thấy thì `is_joined=true`; group mất khỏi snapshot thì `is_joined=false` và giữ `is_delete=false`; page mất khỏi snapshot thì set `is_delete=true`. Friend/group scroll không dùng max cap; dừng sau 3 vòng liên tiếp không tăng số contact hợp lệ đã parse. Zalo friend/group scan branch theo `account.flatformType='zalo'` và chỉ dùng `ZaloRuntimeService` (`getAllFriends`, `getAllGroups`, `getGroupInfo`), lưu meta vào `zalo_users`/`zalo_groups` scoped theo `account_id`, rồi link về `auto_account_contacts.zalo_user_id`/`zalo_group_id`; `zalo_uid`/`zalo_group_id` là account-scoped, không dedupe global. Zalo avatar contact dùng `User.avatar` cho friend và `GroupInfo.avt || GroupInfo.fullAvt` cho group; Zalo group link chỉ lưu field sẵn có (`zalo_groups.link`/`auto_account_contacts.url`) nếu payload trả về, scan không gọi API lấy link như `getGroupLinkDetail`. Zalo group member scan dùng custom endpoint qua `ZaloRuntimeService`: group đã tham gia dùng `/api/group/getmg`, link group join trước rồi dùng `/api/group/getmg`, fallback `getGroupLinkInfo`/`ginfo` với proxy từng request qua setting `zalo.group_link.ginfo_proxy_url`, không login lại zca-js bằng proxy; link scan chỉ update `auto_account_contacts.is_joined` khi join outcome chắc chắn (`joined`/`already_joined` → `true`, `pending_approval` → `false` kể cả group cũ), còn outcome `unknown` không đổi group cũ và group mới mặc định `false`. Page loader chỉ dùng Graph API `me/accounts` sau khi lấy token từ `business.facebook.com/content_management` bằng pattern akaBizAuto `EAAG(.*?)"` và gửi kèm cookies session FB; nếu API/token fail thì báo lỗi, không fallback quét giao diện. Page inbox loader dùng Graph API `/{pageId}/conversations?fields=participants,messages.limit(25){id,message,created_time,from}` với page access token; không set `limit` conversation vì Facebook tự quyết page size theo page/quyền. `contacts:cancel-load` kết thúc lần quét ở data hiện có và vẫn cleanup snapshot như một lần load hoàn tất; completion dùng event `contacts:completed` với payload chuẩn, không parse text progress. Khi chọn vào campaign, picker lưu FB URL vào `auto_campaign_input_data.uid` để workflow nhận raw target chính xác. Group activity text lưu ở `auto_account_contacts.extra_data.lastActivityText`, không ghép vào `name`; `DataScanModal` mặc định lọc bạn bè/group đã tham gia nhưng user có thể đổi `Hiển thị` sang `Tất cả`, và campaign picker có thể chọn cả person/group không còn active nếu user cố tình chọn.

Campaign automation chạy qua [src/main/v2/runtime/backgroundPageManager.ts](src/main/v2/runtime/backgroundPageManager.ts) hidden/offscreen `BrowserWindow` theo từng account để minimized vẫn render ổn định. Renderer không tự chuyển page/focus; BrowserPage chọn sẵn account bằng `campaign:browser-select` và hiển thị preview stream bằng `campaign:browser-preview` để user tự vào quan sát. Test/editor vẫn dùng `PageControllerRegistry` của webview visible.

Convention quan trọng (xem memory `campaign_conventions.md`):
- **C# Facebook DOM workflow reference**: khi user cung cấp code C# Facebook automation đã chạy đúng, xem code C# là source-of-truth cho mọi tương tác DOM trong workflow. Trigger nhanh rule này khi user nói các cụm như `C# DOM mode`, `trust C#`, `bám C#`, `làm giống C#`, hoặc `đối chiếu DOM theo C#`. Bắt buộc bám sát C# nếu user không yêu cầu khác: XPath selector giữ nguyên; parent/root dùng để find element giữ nguyên; thứ tự thao tác DOM giữ nguyên; click/scroll/sleep/poll phải mô phỏng đúng hành vi C# nhất có thể trong Electron workflow; không tự thêm fallback selector, selector tiếng Anh, contains-class thay exact-class, visible filter, scroll container fallback, hoặc DOM heuristic khác. Được phép khác C# ở logic ngoài DOM nếu phù hợp hệ thống: lưu DB/upsert/dedupe, logging/progress/cancel, workflow variables, stop policy như `maxNoChangeCycles` nếu user chấp nhận. Trước khi implement workflow từ C#, agent phải trình bày bảng đối chiếu `C# step | Workflow step dự kiến | Khác C# không | Lý do`; nếu cần khác C# ở phần DOM, phải hỏi user trước.
- **Atomic blocks**: tuyệt đối KHÔNG tạo "do-many-things" block. Compose existing primitives (`page.click`/`page.type`/`page.waitForSelector`/...).
- **KHÔNG dùng tọa độ viewport** — webview có thể không focus, `getBoundingClientRect()` clientX/clientY có thể sai. Dispatch synthetic event với `{bubbles, cancelable, view: window}` (no coords).
- **FB timestamp link** lazy-load qua `FocusEvent('focusin')`, không phải hover.
- **Fanpage UI post link**: `fb_post_current_identity_ui` lấy link sau khi composer đóng bằng `FbComposerRawPostLink` → render wait → `FocusEvent('focusin')` → `FbComposerPostLink`; nếu `postUrl=''` nhưng `posted=true` thì vẫn log đăng thành công, chỉ thiếu link.
- Group post click popup optional `GroupPostDismissDialogOrUsePageButton` sau khi vào group và sau verify submit; sau `fb_click_post_button` phải chạy `fb_verify_group_post_form_closed`, link lấy qua `GroupPostRawPostLink` → `FocusEvent('focusin')` → `GroupPostPostLink`; `fb_detect_pending_post` kết luận pending bằng `/pending_posts/` hoặc page phụ `/my_pending_content` qua `helpers.checkGroupPendingContent` ([migration_v37_group_post_link_after_publish.sql](migrations/migration_v37_group_post_link_after_publish.sql), [migration_v92_group_post_pending_content_detect.sql](migrations/migration_v92_group_post_pending_content_detect.sql)).
- Group post frequency limit: nếu form đăng bài không đóng sau 60s và thấy `GroupPostFrequencyLimitError` (`//*[contains(.,'giới hạn tần suất bạn đăng bài')]`), block `fb_verify_group_post_form_closed` phải throw để scheduler map `err_group_post_frequency_limit` và `tạm dừng` campaign ngay, không chờ ngưỡng `err_undefined` ([migration_v99_group_post_frequency_limit_error.sql](migrations/migration_v99_group_post_frequency_limit_error.sql)).
- Sau group post verify thành công, scheduler upsert group contact theo account từ output `fb_detect_pending_post`: pending true → `requires_post_approval=true`, check kết luận không pending → `false`, check inconclusive/không dựng được URL thì giữ `null`; group do campaign insert mặc định `is_joined=false` ([migration_v39_account_contact_group_status.sql](migrations/migration_v39_account_contact_group_status.sql)).
- Group post comment: `commentGroupMode` filter sau khi biết pending; pending `own` bỏ qua, pending `others` shift về bài đầu tiên, pending `all` giữ `[1..N]` bài đang thấy ([migration_v40_group_post_comment_options.sql](migrations/migration_v40_group_post_comment_options.sql)).
- Group post skip known approval: `skipPostIfGroupRequiresApproval` tra `auto_account_contacts.requires_post_approval`; nếu `true` thì workflow bỏ composer/post nhưng vẫn đi nhánh comment với pending từ account contact ([migration_v41_skip_group_post_known_approval.sql](migrations/migration_v41_skip_group_post_known_approval.sql)).

### Workflow engine v2

[src/main/v2/runtime/](src/main/v2/runtime/) — engine duy nhất chạy campaign:
- `workflowEngine.ts` — DAG executor cohort-based: parallel split (multiple outgoing edges), AND/OR join (mode='all'/'any' merge node), `ifElse` skip propagation, loop body re-exec với `vars.loopItem`/`vars.loopIndex`, `AbortSignal` cancellation. `allSteps[]` track loop iterations để scheduler log đầy đủ (snapshot `nodeStates` chỉ giữ iteration cuối).
- `blockExecutor.ts` — `vm.createContext` sandbox. KHÔNG expose `process`/`require`/`Buffer`/`fs`. Block code = JS string, return object → output, throw → fail.
- `pageController.ts` — wrap `webContents.executeJavaScript` thành API `page.click/type/fill/scroll/evaluate/$$/waitForSelector/uploadFile/dropFile/dropFileDeep/apiCall/downloadUrl`. Hỗ trợ XPath union `|` và CSS. Có fallback scroll cho FB comment box lazy-render; `dropFileDeep` tìm drop target cả trong iframe cùng origin.
- `backgroundPageManager.ts` — hidden/offscreen browser pages cho scheduler, shared persistent partition với visible webview theo account.
- `blockHelpers.ts` — `sleep`/`log`/`randomBetween`/`normalizeFbUrl`/`extractUidFromInput`/`splitVariants`/`cycleVariant`/`element(name)`/`elementWith(name, vars)`/`checkGroupPendingContent(opts)`. `element` query cached `auto_elements`; `checkGroupPendingContent` do scheduler inject runtime helper, mở temporary background page cùng partition account và stream preview page phụ. Helper mở rộng để block DB ghi log cấu trúc phải dùng optional names như `logRunEvent`/`logRunEvents`; nếu runtime chưa implement thì helper trả unsupported/no-op, còn helper sai tên ngoài whitelist vẫn lỗi để bắt typo. Khi helper được implement, engine tự bơm metadata `run_id`/`run_step_id`/`node_id`/`block_name`/campaign/input/account vào `auto_campaign_run_events`; block chỉ truyền event payload.
- Node config runtime `screenshotCaptureTiming` + `screenshotCaptureOn` là metadata universal của workflow engine, không truyền vào `input` block và không ghi vào step output. Phase hiện tại chỉ capture sau block; PNG lưu local dưới `app.getPath('userData')/local-data/block-screenshots`, metadata user-facing ghi vào `auto_campaign_run_events.event_type='browser_screenshot'` với `debug_data.screenshotPath`. Screenshot event metadata lưu kết quả chiến dịch/action dễ hiểu (`Đăng bài thất bại...`, `Lỗi đăng bài...`, policy `auto_error` nếu có); `block_name/node_id` chỉ là metadata debug, không làm text chính cho user.
- Built-in `fb_resolve_url` resolves URL input in this order: `input.raw`, `vars.inputDataUid`, `vars.targetUrl`. DB rows are the source of truth for built-in blocks/workflows/elements.
- Bảng: `auto_blocks`, `auto_workflows`, `auto_elements`, `auto_runs`, `auto_run_steps` (BIGSERIAL id, UNIQUE name).

[campaignScheduler.ts](src/main/services/campaignScheduler.ts) chọn workflow theo current staff: `org_staff.use_test_workflow=false` dùng `auto_campaign_actions.workflow_id`, `true` dùng `test_workflow_id`; khi bật test mà action thiếu `test_workflow_id` thì giữ campaign `'chờ xử lý'` với note, không fallback sang workflow thật.

### Campaign system

Domain (sau migration_v4 drop engine v1):
- `auto_accounts` — tài khoản/social profile để login và chạy automation (trước đây là `org_accounts`); `proxy_id` nullable FK → `auto_proxies.id` để gắn proxy theo account; `rate_limit_minutes` là số phút khung check giới hạn giờ copy vào campaign khi lưu, default/fallback `65`, hiện không chỉnh ở UI account. Với Zalo, credential/session nằm trực tiếp ở `zalo_session` + timestamp/error fields trên `auto_accounts`; repository/list account/preload mặc định chỉ trả `hasZaloSession` và identity fields an toàn, KHÔNG expose raw `zalo_session` ra renderer. Với Email, SMTP config nằm ở `email_session` + timestamp/error fields; tạo account bắt buộc verify SMTP, sửa metadata không verify lại nếu config không đổi.
- `zalo_accounts` — shared identity catalog cho Zalo, dedupe toàn hệ thống bằng `zalo_uid UNIQUE`; lưu `display_name`, raw `phone`, `avatar_url`, metadata profile không-secret. Nhiều `auto_accounts` có thể trỏ cùng `zalo_account_id`; credential không được lưu ở bảng này.
- `zalo_users` / `zalo_groups` — meta danh bạ Zalo theo account, unique `(account_id, zalo_uid)` và `(account_id, zalo_group_id)` vì cùng một user/group Zalo có thể ra UID khác nhau theo tài khoản quét. Mỗi top-level field quan trọng từ `zca-js` có column riêng, object/array phức tạp giữ `jsonb`/`text[]`, `raw_payload` chỉ để audit; `zalo_groups.link` nullable dành cho cơ chế lấy link sau này, không được fetch thêm trong contact scan hiện tại.
- `zalo_group_members` — membership snapshot theo account/group/user, unique `(account_id, zalo_group_id, zalo_uid)`, FK tới `zalo_users`/`zalo_groups`, lưu role (`owner`/`admin`/`member`), `role_rank`, `is_current`, `raw_payload`, `last_seen_at`; re-scan group phải set `is_current=false` cho member không còn thấy. Member mirror vào `auto_account_contacts` dạng `person` theo `uid=zalo_uid` và giữ `is_friend=true` nếu trước đó đã là bạn bè.
- `auto_proxies` — kho proxy staff-scoped dùng chung cho nhiều account; hỗ trợ `http`/`https`/`socks5`, credential lưu DB và mask ở UI. Không cho xoá proxy đang được account dùng. Đổi proxy account hoặc sửa proxy chỉ update DB, không đụng runtime hiện tại nên được phép kể cả khi account/campaign đang chạy; proxy mới chỉ áp dụng khi session được prepare ở lần chạy/reload sau.
- `auto_status` — catalog trạng thái một bảng dùng cho UI/options; `code` là unique identifier để sau này có thể constraint/FK một cột (ví dụ `account_pending`, `campaign_pending`), các cột còn lại chỉ là metadata (`status_key`, `flatform_type`, `component_type`, default/terminal/manual flags). Hiện chỉ là lookup, chưa thay các cột text runtime như `auto_accounts.status`/`login_status` hoặc campaign status bằng FK.
- `auto_account_contacts` — danh bạ person/group/page theo account (trước đây là `org_account_contacts`); person dùng `is_friend` để lưu trạng thái bạn bè (`NULL` = chưa có API xác nhận), group dùng `is_joined` và `requires_post_approval` nullable để lưu trạng thái tham gia/duyệt bài. Tag akaBiz nội bộ gắn trực tiếp bằng `akabiz_tag_ids bigint[]`; một contact có thể có nhiều tag. Dữ liệu legacy `contact_type='friend'` chỉ đổi sang `person` qua script manual `migrations/manual_update_friend_contacts_to_person.sql`, không chạy tự động trong migration feature.
- `auto_contact_tags` — catalog tag akaBiz staff-scoped, soft delete bằng `is_delete`, unique active theo `(staff_id, lower(name))`; membership không dùng bảng join riêng mà lưu trong `auto_account_contacts.akabiz_tag_ids`.
- `auto_account_contact_groups` / `auto_account_contact_group_members` — nhóm data theo `account_id + contact_type + purpose`; `purpose='data_group'` là nhóm data thường, `purpose='zalo_friend_blocklist'` là danh sách không gửi tin cho chiến dịch `zalo_message_friend`. Một contact có thể nằm nhiều nhóm; membership unique `(group_id, contact_id)` nên thêm trùng phải dùng upsert/ignore duplicate, không nhân đôi. `DataScanModal` chỉ quản lý nhóm `data_group`; danh sách không gửi tin Zalo có IPC/UI riêng trong Cài đặt chung. Khi chọn nhiều nhóm data vào campaign phải union contacts rồi lọc trùng trước khi insert snapshot vào `auto_campaign_input_data`.
- `auto_content_templates` — kho mẫu nội dung text theo `staff_id`; chỉ lưu `name` + `content`, soft delete bằng `is_delete`, chặn trùng tên active và trùng nội dung trong cùng staff; campaign form chỉ copy nội dung mẫu vào `auto_campaigns.content`/`extra_settings.commentContent`, không đổi scheduler/runtime.
- `auto_campaigns` — campaign config (action_id, account_id, schedule, original_schedule, daily_stop_time, content, extra_settings). `schedule` là next runtime schedule scheduler có thể tự đổi; `original_schedule` là lịch/giờ gốc do user tạo/sửa, dùng làm anchor giờ khi runtime schedule đã bị automation đẩy tới. Status runtime hợp lệ: `'chờ xử lý' | 'đang chạy' | 'tạm dừng' | 'hoàn thành'` (`'lỗi'` không còn là campaign status hợp lệ; lỗi action-level nằm ở `auto_campaign_details`). `daily_stop_time` là giờ dừng trong ngày (`time`, Asia/Ho_Chi_Minh); `getPendingCampaigns()` bỏ qua campaign sau giờ này. `completed_at` set khi status chuyển `'hoàn thành'`; `last_run_at` do trigger detail cập nhật từ `auto_campaign_details.created_at`.
- `auto_campaign_actions` — template loại campaign (`facebook_group_post`/`facebook_timeline_post`/`facebook_page_post`/`facebook_message_friend`/`facebook_message_uid`/`facebook_find_data_group`/`facebook_find_data_search`/`facebook_comment_seeding`/`facebook_comment_seeding_post`/`facebook_join_group`/`email_send`/`zalo_message_phone`/`zalo_message_friend`/`zalo_message_group`/`zalo_message_birthday`/`zalo_message_group_member`/`zalo_message_group_realtime`/`zalo_message_remarketing_customer`/`zalo_message_friend_recommendation`/`zalo_join_group_link`); `workflow_id` là workflow thật, `test_workflow_id` là workflow test riêng từng action. Deleting a real source campaign is blocked if it is `đang chạy` or still linked to another target; deleting a draft source only removes it from the current form state. Target campaigns with at least one selected find-data source may have no manual `auto_campaign_input_data`; scheduler leaves them in `chờ xử lý` with note `"Đang chờ data từ chiến dịch tìm data"` and does not write a campaign log for that wait state. Detail dock relation tabs use `listCampaignRelationSummaries`: "Chờ gửi" counts `auto_campaign_input_data.status='chờ xử lý'`, while "Thành công"/"Thất bại" are `auto_campaign_details` breakdowns by `action_name` (`lỗi` grouped into thất bại but labeled).

**Recovery**: `resetRunningStatuses(staffId)` staff-scoped chạy sau login, trước logout và trước app quit (accounts + campaigns + campaign_inputs + campaign_input_data) — flip rows kẹt `'đang chạy'` về `'chờ xử lý'` (đề phòng crash mid-flow), không chạy global trước login. `recoverStuckCampaignInputData(campaignId, errMsg)` flip input_data stuck thành `'hoàn thành'` + `note=errMsg` khi outer catch (enum không có `'lỗi'`). `stop()` cũng đóng toàn bộ hidden background pages để không giữ tài nguyên nền.

**Schedule maintenance**: sau scoped recovery lúc login, `maintainCampaignSchedules()` ([campaignRepository.ts](src/main/data/repositories/campaignRepository.ts)) dọn campaign stale theo ngày `Asia/Ho_Chi_Minh`; day-change watcher trong [handlers.ts](src/main/ipc/handlers.ts) gọi lại khi app treo qua đêm. Daily/weekly/monthly dùng giờ từ `original_schedule ?? schedule` để tính lịch mới; automation chỉ update runtime `schedule`, còn user tạo/sửa campaign mới update cả `schedule` và `original_schedule`. Với daily còn `'chờ xử lý'`, `continueNextDay=true` nghĩa là qua ngày sẽ dời runtime `schedule` sang giờ hẹn của ngày mới; `continueNextDay=false` giữ lịch cũ đã quá hạn để scheduler chạy ngay khi đủ điều kiện. Checkbox này không quyết định "có chạy tiếp hay không"; campaign đã `'hoàn thành'` không tự bật lại. Weekly/monthly `refreshData=true` reset `auto_campaign_input_data` rồi bật lại `chờ xử lý`; completed no-refresh chỉ update `schedule`.

**Rate limit** ([campaignRepository.ts:getAccountRateLimitStatus](src/main/data/repositories/campaignRepository.ts)) dùng `action_code`:
- Daily limit so với `auto_account_action_status.count_action_in_day` (reset 00:00 Asia/Saigon).
- Hourly/window limit query `auto_campaign_details` theo `(account_id, action_code, created_at)` và đếm `counts_toward_limit=true` hoặc `counts_toward_limit IS NULL AND status IN ('thành công','thất bại')`; đừng default cột này thành `true` vì sẽ đổi nghĩa legacy/Facebook.
- ActionManagerModal stores candidate quota checks in `auto_campaign_actions.limit_check_action_codes`; Campaign form auto-saves visible quota checks to `extra_settings.actionLimits.enabledActionCodes` for scheduler compatibility. `enabledActionCodes` only controls daily/window quota checks; scheduler must still enforce `auto_account_action_status.is_disable` for every executable action even when that action code is absent from `enabledActionCodes`.
- Campaign form stores thresholds in `extra_settings.actionLimits.byActionCode[action_code]`; `rateLimitMinutes` is copied from `auto_accounts.rate_limit_minutes` per account when saving, fallback `65`; scheduler also filters out checks for campaign actions disabled by toggles such as `enableAddFriend=false`.
- Limit notes/logs must include the exact action name; `auto_error` messages may use `[a]`/`[action]` and `[action_code]` placeholders.
- Khi hit limit/disable action: campaign về `'chờ xử lý'`, ghi `note`; KHÔNG đổi schedule.

### Data layer

[src/main/data/repositories/](src/main/data/repositories/) — mỗi entity 1 file. Pattern:
- `client = () => getSupabaseClient()` ([supabaseClient.ts](src/main/data/supabaseClient.ts))
- `requireCurrentUser()` ([currentUser.ts](src/main/data/currentUser.ts)) ném lỗi nếu chưa login → block IPC handler
- `mapXxxFromDB(row)` trong [mappers.ts](src/main/data/mappers.ts) chuyển snake_case → camelCase
- Built-in records live in Supabase DB (`auto_blocks`, `auto_workflows`, `auto_elements`) and DB is the source of truth. There is no `seedV2` runtime/source fallback; update built-ins via admin UI/IPC or explicit SQL migration.

- Central AI config uses non-`auto_` tables `ai_model`, `ai_prompt`, `ai_personalization`, `ai_using`, and `ai_log`; `aiRuntimeService.callAiUsing(code, payload, metadata)` loads `ai_using.code`, renders prompt templates with `[key]`/`{{key}}`, calls provider endpoints, and writes sanitized `ai_log` rows. Never log raw `ai_model.api_key`.
- `aiRuntimeService.callAiUsing()` supports `imageDataUrl`/`imageDataUrls` for vision-capable providers and must mask data URLs/base64 in `ai_log.sanitized_request`; scheduler uses `campaign_error_screenshot_diagnosis` only as best-effort diagnosis for `err_undefined` threshold logs when a prior `browser_screenshot` exists.
- Workflow blocks call centralized AI only through optional `helpers.callAIUsing(code, payload)`. Built-in AI blocks are promoted in DB to use `ai_using.code` directly and should not depend on workflow `codeOverride`, legacy helper shims, or `api.akaapp.vn`.
- Facebook campaign assistant context is built in [aiHandlers.ts](src/main/ipc/handlers/aiHandlers.ts): send sanitized full campaign/account/action, full `auto_campaign_input_data` + `auto_campaign_details`, progress logs for today or latest `max_context_rows`, account action limits, and `bugLogs` from campaign error details, account error states with `auto_error`, plus `auto_runs/auto_run_steps` traces limited to error steps with 2 neighboring steps. Assistant chat calls centralized AI using `app_campaign_assistant_chat`; always mask secrets, file paths, and base64-like blobs before sending context.
- Account action reports use [reportRepository.ts](src/main/data/repositories/reportRepository.ts) for summary/detail IPC; renderer must request aggregated/detail pages and must not pull raw campaign logs to build report matrices client-side.
- `org_staff.akabiz_integrations` stores current-staff external akaBiz connections (`sms`/`zaloWeb` plus `akaBizDesktop` with `installPath`/`dbPath`); use [staffIntegrationRepository.ts](src/main/data/repositories/staffIntegrationRepository.ts), not renderer local storage.
- Auth login khóa `org_staff` theo 1 máy qua `device_fingerprint_hash` (SHA-256 platform + OS machine ID) trong [authRepository.ts](src/main/data/repositories/authRepository.ts) + [deviceIdentity.ts](src/main/services/deviceIdentity.ts). Product id/label/order map tập trung ở [authProductCatalog.ts](src/shared/authProductCatalog.ts): `3=facebookCore/Facebook`, `10=facebookFanpage/Fanpage`, `13=email/Email`, `16=zalo/Zalo`; renderer không hardcode lại mapping này. Sau login, backend list/guard/scheduler dùng snapshot `AuthUser.entitlements`; `AuthUser.accountProducts` chỉ dùng để hiển thị thông tin tài khoản và gồm các row product active/non-deleted đã được main process enrich `displayName/displayOrder`. Không query live trong interval hoặc khi chạy campaign. Chỉ login/autologin và session-expiry watchdog trong `handlers.ts` được refresh live: check ngay sau login/autologin và hằng ngày lúc 00:05 Asia/Ho_Chi_Minh; nếu không còn entitlement nào, main process tự cleanup rồi emit `AUTH_SESSION_EXPIRED`, còn nếu entitlement/product snapshot đổi nhưng vẫn còn gói thì emit `AUTH_USER_UPDATED` để renderer reload user/accounts/campaigns/actions. RLS policy `org_organization_product_read_all` cho anon/authenticated SELECT bảng này để app desktop tự kiểm tra; không mở quyền ghi. Login UI phải hiển thị lỗi nghiệp vụ thân thiện và lọc prefix IPC/PostgREST/schema cache, không show log kỹ thuật cho user. Đổi mật khẩu dùng `AUTH_CHANGE_PASSWORD`, kiểm tra mật khẩu cũ rồi update `org_staff.password`; `AuthUser.isAdminAkabiz` lấy từ `org_staff.is_admin_akabiz`, không dùng `staffId === 1`; `AuthUser.useTestWorkflow` lấy/lưu từ `org_staff.use_test_workflow`.
- Akachat customer ingestion lives in Supabase Edge Functions: [insert_aka_customer](supabase/functions/insert_aka_customer/index.ts) resolves owner by existing owner → `staff_id`/`chat_staff_id` → `aka_data_split_rules`, then calls [create-aka-crm](supabase/functions/create-aka-crm/index.ts). Migration [migration_v71_akachat_customer_crm_split.sql](migrations/migration_v71_akachat_customer_crm_split.sql) creates split rules and disables the old `trg_aka_customer_split_create_crm` trigger.

- Screenshot progress log là artifact-only (`📸 Ảnh chụp màn hình trạng thái trình duyệt`), ghi sau log kết quả action khi match được step, có thể kèm action realtime `block_screenshot_preview` để nút `Xem` mở ảnh trong app; raw `auto_campaigns.log` được thêm marker ẩn `<!-- screenshotEventId:N -->` để match event, UI phải strip marker và không được lưu local file path vào log text.
- Khi campaign chạm ngưỡng lỗi liên tiếp, log `⚠️ Chiến dịch đã lỗi/thất bại liên tiếp...` dùng root cause từ `auto_campaign_details.data.error`; riêng `err_undefined` có screenshot thì AI diagnosis có thể thay root cause, nhưng không được đổi policy/counter/status.

**Per-milestone logging**: post xong ghi 1 row, mỗi comment ghi 1 row, friend request ghi 1 row — KHÔNG đợi cuối flow. Lý do: nếu comment failed sau khi post OK, vẫn phải có row "Đăng bài thành công" để khách hàng thấy. Với `fb_comment_at_position`, lỗi ở một bài trả `commentFailed=true`/detail `thất bại` và loop vẫn tiếp tục bài sau; chỉ khi không có milestone thành công nào thì target comment seeding mới bị tính bad.

## Common pitfalls

- **Loop iterations**: scheduler `logMilestonesV2` đọc `result.steps` từ engine. Engine v2 maintain `allSteps[]` (mỗi loop iteration 1 row riêng) thay vì snapshot `nodeStates`. Khi đọc per-iteration data, đọc `s.output` (block return value), KHÔNG `s.input` (chỉ là config + parents trực tiếp).
- **Skipped action steps**: `logMilestonesV2` must ignore `status='skipped'` action blocks. Optional workflow branches (e.g. `enableAddFriend=false`) still return snapshot steps, but they are not real user actions.
- **Newsfeed interaction**: `fb_newsfeed_*` blocks should skip unreadable/non-actionable posts instead of failing the whole run; only `liked === true` / `commented === true` action outputs should create `auto_campaign_details` rows. `enablePostLike`/`enableComment`, not kind text, gate runtime/quota; partial quota and pause abort must stay gated to `facebook_newsfeed_interaction`. Keep newsfeed action selectors scoped to the current `postEle`; `findActionRoot`/ancestor normalization can include comment DOM and click/comment the wrong target.
- **Comment seeding keyword miss**: `fb_prepare_seeding_iterations` có thể trả `commentIterations=[]`; loop body chỉ chạy bên trong loop executor, keyword/text phải normalize bỏ dấu + whitespace, và text bài phải lấy bằng `fb_post_in_uid` + `fb_content_in_post_in_uid` thay vì raw `[role=article]` ([migration_v14_comment_seeding_find_data_content.sql](migrations/migration_v14_comment_seeding_find_data_content.sql)).
- **Comment image-only logs**: `fb_comment_at_position` có thể return `text=''` nhưng `imageCount>0`; `logMilestonesV2()` vẫn phải tạo row Comment, không skip theo text rỗng ([campaignScheduler.ts](src/main/services/campaignScheduler.ts), [migration_v18_comment_images.sql](migrations/migration_v18_comment_images.sql)).
- **Output cascade**: engine v2 KHÔNG có inputMapping — output của parent merge vào input của child theo edges, last-write-wins. Output `scrapedText` của block ở xa KHÔNG cascade qua chain — nếu cần dùng ở downstream chain dài, **mutate `vars`** thay vì rely on input merging.
- **XPath union `|`**: timeline page và group page dùng selector khác nhau. Element store XPath với `|` để match cả hai. `document.evaluate` (XPath 1.0) hỗ trợ union, trả node đầu tiên match.
- **`auto_runs.workflow_id` column**: tên cột là `workflow_id` nhưng FK → `auto_workflows.id` (BIGINT). Đừng nhầm với cột `workflow_id` (UUID) đã drop ở migration_v4 thuộc `auto_campaign_actions`.
- **timeSleepBetween2** vs **actionLimits.sleepBetweenActions**: scheduler ưu tiên `actionLimits.sleepBetweenActions`, fallback `campaign.timeSleepBetween2`. Cả 2 tính bằng giây; `0` là giá trị hợp lệ cho campaign up tin nên scheduler/repository phải dùng `??`, không dùng `||`.
- **Schedule edit** (`scheduleEndDate`): cột nullable, type `string | null | undefined`. Pass `null` (không phải `undefined`) để clear — `updateCampaign`'s `!== undefined` check sẽ skip undefined. Cho `scheduleType='daily'`, luôn gửi `null` (form date input disabled nhưng formData vẫn giữ default 7-day-ahead, sẽ silently stop campaign sau 1 tuần).
- **Hidden vs disabled toggle** (`sharePost` pattern): feature có DB flag nhưng chưa implement → ẨN khỏi UI (don't render checkbox), giữ flag trong `formData` + `handleSave` payload (preserve roundtrip), backend log warning per run. KHÔNG `<input disabled>` (leak feature name).
- **Minimized campaign runs**: scheduler chạy campaign bằng hidden/offscreen `BackgroundPageManager`; visible webview có thể không paint khi minimized/hidden nên chỉ dùng cho login/test/manual. BrowserPage quan sát qua preview stream.
- **Zalo and Email are browserless for now**: Zalo account management uses `zca-js` API sessions only; Email uses SMTP/nodemailer only. Do not add Zalo or Email to BrowserPage tab lists, `prepareAccountBrowserSession`, `<webview partition="persist:account_${id}">`, or `WebviewRegistry` until product explicitly enables browser-based runtime.
- **Entitlement snapshots**: product gates are live-refreshed only at login/autologin and the daily session-expiry check. UI and backend guards use `AuthUser.entitlements` snapshots between those checks; do not add `org_organization_product` queries to scheduler/account poller/realtime managers/list repositories to "be safer". Admin campaign action management is configuration and should not filter out Email.
- **Zalo API-only campaigns**: `zalo_message_phone`, `zalo_message_friend`, `zalo_message_group`, `zalo_message_birthday`, `zalo_message_group_member`, `zalo_message_group_realtime`, `zalo_message_remarketing_customer`, `zalo_message_friend_recommendation`, and `zalo_join_group_link` run workflow v2 with `page=null`; helpers must call `ZaloRuntimeService.ensureApi(accountId)`. Scheduler verifies Zalo login with `checkSession()` before marking campaign running, logs raw campaign API failures to `zalo_api_error_logs`, and must not create browser/profile side effects.
- **Zalo join group by link**: input data stores the group link in `auto_campaign_input_data.uid`; accept and normalize `zalo.me/g/...` and `zaloapp.com/qr/g/...` to `https://zalo.me/g/...` in upload/runtime. `joinGroupLink` code 178 creates detail status `đã tham gia` with `counts_toward_limit=false` and no `error_code`; code 240 is `thành công`, counts quota, and mirrors group contact with `is_joined=false`.
- **Zalo group theo thời gian thực**: listener lifecycle stays in `ZaloRuntimeService`; [zaloRealtimeGroupCampaignManager.ts](src/main/services/zaloRealtimeGroupCampaignManager.ts) only routes `group_event`/`message`/`reaction` into campaign data. Received/duplicate data logs go to `auto_campaigns.log` ("Lịch sử chạy"), not `auto_campaign_details` ("Kết quả chạy") and not the progress panel.
- **Zalo campaign user upsert**: user-target Zalo campaigns may upsert `zalo_users` + `auto_account_contacts.person`, but only from metadata actually returned by Zalo API (`findUserByPhone`, `getAllFriendsPage`, `getUserProfile`). Do not populate contact metadata from `auto_campaign_input_data`; do not set `is_friend=false` unless API returns an explicit `isFr`/friend status. `zalo_message_group` does not upsert groups or fetch extra group metadata.
- **Zalo share message mode**: friend/group campaign option `extraSettings.zaloMessageSendMode='share'` bypasses workflow execution after scheduler preflight and sends text via raw Zalo `/api/message/mforward` or `/api/group/mforward` in batches up to 50. Do not use `zca-js api.forwardMessage` for campaign share mode because it reuses one `clientId` for the whole batch; build per-target `clientId` values and map success/fail by `clientId` (or target id when Zalo returns one). Skip own UID before sending friend share batches so one self target does not make Zalo reject the entire batch with `114`.
- **Zalo friend "Danh sách không gửi tin"**: `zalo_message_friend` can enable `extraSettings.zaloFriendBlocklistEnabled` with a contact group `purpose='zalo_friend_blocklist'` scoped to the same account. Scheduler loads UID snapshot once, checks before quota/workflow/API/share batch, marks skipped input data `hoàn thành` with note/date, does not create `auto_campaign_details`, and does not count quota. Normal mode logs each skipped target in progress; share mode logs only the total skipped count.
- **Zalo remarketing customer picker**: `zalo_message_remarketing_customer` selects targets from previous Zalo message `auto_campaign_details`, but detail JSON is only history/fallback. Resolve display data from `auto_campaign_input_data`, `zalo_users`, `auto_account_contacts`, `zalo_group_members`, and `zalo_groups`; friend status must come from `auto_account_contacts.is_friend` or `zalo_users.is_fr`, not `data.target.isFriend`.
- **Zalo auto-materialized input data**: `zalo_message_friend` modes `all_friends`/`tagged_friends` materialize friend rows only once per campaign and clone must not copy those rows or materialized markers. `zalo_message_friend_recommendation` calls `getFriendRecommendations()` once per campaign/account at runtime, materializes UID/name/phone only into `auto_campaign_input_data`, marks empty results as completed, and upserts contacts only later when resolving each UID. `zalo_message_birthday` materializes by run date from `getAllFriendsPage(...).sdob.slice(0, 5) === dd/mm`; daily is one-shot, while weekly/monthly soft-delete old birthday input rows and clear birthday materialized metadata before the next occurrence.
- **Zalo contact scan is API-only**: friend/group/group-member data scans must go through `ZaloRuntimeService`; do not create webviews/browser profiles and do not call extra link APIs during group scan. Friend/group scans may call `getLabels()` once to sync Zalo label catalog (`contact_type='zalo_tag'`) and mirror tag membership from `label.conversations` into `auto_account_contacts.extra_data.zaloTagIds`/`zaloTagNames`/`zaloTags`; do not backfill Zalo tags from old `auto_campaign_details`. `DataScanModal` should keep Facebook table columns stable; Zalo-only avatar/phone/tag columns are gated by platform, while Zalo group `Link` displays the stored nullable `auto_account_contacts.url`. DataScan Zalo tag/akaBiz tag filters are query state sent through shared list query types and main repositories (not renderer-only UI filters); keep multi-select OR within each tag filter, AND between Zalo tag and akaBiz tag filters, and preserve the `Chưa gắn tag` flags. Group-member link mode may decode QR payloads like `zaloapp.com/qr/g/...` but must normalize them to `https://zalo.me/g/...` before calling runtime.
- **DataScan pagination/selection**: non-Page-Inbox data tables use backend pagination/search/export through account contact, Zalo group member, or Zalo remarketing list APIs; default page size is 100. Header checkbox selects all matching backend filters across pages, tracks exclusions, and export/add-to-campaign/create-group must fetch the backend selection instead of only current page rows. Page Inbox keeps its existing local SQLite pagination path.
- **Zalo session single-use/race**: one Zalo session should not be logged in concurrently by multiple API instances for the same `auto_account`. `ZaloRuntimeService` serializes login through `apiLoginInflight` and serializes verify/retry through `verifyInflight`; keep new Zalo tasks behind `ensureApi(accountId)` and avoid direct `zalo.login(session)` calls.
- **Zalo credential exposure**: `auto_accounts.zalo_session` is secret runtime credential. Account list mappers/preload/UI must not return raw cookies/session to renderer; only main process Zalo runtime/repository methods may read/write it.
- **Minimized data scans**: `ContactLoader` cũng chạy bằng hidden/offscreen `BackgroundPageManager` + workflow v2 built-in. Không đưa logic scrape mới về visible webview; nếu cần đổi selector/logic quét thì seed/update `auto_blocks`/`auto_workflows` bằng migration.
- **FB image upload**: `page.dropFile()` must avoid viewport coordinates in hidden/offscreen pages; `fileCount` only means files were injected, not that FB rendered an attachment preview ([pageController.ts](src/main/v2/runtime/pageController.ts)). Comment-image workflows support exactly 1 image/comment; `fb_comment_at_position` drops into the dialog textbox after clicking the indexed comment box.
- **Comment dialog textbox**: `fb_comment_at_position` clicks `fb_comment_box_at_n` to open/focus the target post composer, then pastes comment text with `page.fill()` into `fb_comment_dialog_textbox` from `auto_elements`; this matches akaBizAuto `CommonSeleniumService.DispatchPaste` and preserves multiline content. Images still use `dropFile()` on the textbox ([migration_v32_comment_dialog_textbox_element.sql](migrations/migration_v32_comment_dialog_textbox_element.sql), [migration_v91_promote_comment_paste_to_blocks.sql](migrations/migration_v91_promote_comment_paste_to_blocks.sql)).
- **Direct post comment seeding**: `fb_comment_current_post` uses `fb_comment_dialog_textbox` from `auto_elements` for paste/drop/focus; do not tag DOM nodes with `data-akabiz-current-post-comment-box` or click the main “Bình luận/Comment” action button ([migration_v33_comment_current_post_use_dialog_element.sql](migrations/migration_v33_comment_current_post_use_dialog_element.sql), [migration_v91_promote_comment_paste_to_blocks.sql](migrations/migration_v91_promote_comment_paste_to_blocks.sql)).
- **Find-data post links**: `PostLinkInUid` can also see comment permalinks under a post. Reject `comment_id`/`reply_comment_id` before pushing links into `facebook_comment_seeding_post` ([migration_v25_find_data_post_links_ignore_comments.sql](migrations/migration_v25_find_data_post_links_ignore_comments.sql)).
- **Find-data fan-out dedupe**: UID/post link/phone/Zalo group link dedupe against the source campaign's `"Tìm data"` detail JSONB before push; do not query target campaign/external detail for dedupe unless product changes this rule.
- **Group post frequency limit**: không return `ok:false` cho lỗi `giới hạn tần suất bạn đăng bài`; phải throw từ `fb_verify_group_post_form_closed` để workflow dừng downstream và scheduler apply `err_group_post_frequency_limit` ngay.
- **akaBiz Desktop SQLite**: user selects install folder, DB path is `<installPath>/Resources2/akabiz_auto_local.db`; phone campaign actions are `zalo_addfriend`/`zalo_send_to_phone`, group-link action is `zalo_join_group_link`, inserts write `Phone` or `Uid` only with `Status=1` and `IsAutomate=1` (no `SortOrder`, no `GroupUserId`).
- **Message template tokens**: `#{FULL_NAME}` is resolved inside `fb_send_message` after Messenger opens via `//*[contains(@class,'xxymvpz x1dyh7pn')]`; if missing, replace with `''`. Date tokens use `#{TODAY|TOMORROW|YESTERDAY(DD/MM/YYYY|MM/DD/YYYY)}` ([migration_v28_message_template_tokens.sql](migrations/migration_v28_message_template_tokens.sql)).
- **Electron navigation errors**: hidden page preload can be superseded by workflow `page.navigate()`; `src/main/v2/runtime/pageController.ts` treats `ERR_ABORTED`/`-3` as non-fatal. Facebook `ERR_FAILED (-2)` is only retried when `will-prevent-unload` fires, because that means a draft/form beforeunload prompt blocked automation navigation.
- **Emojis trong source files**: KHÔNG viết emoji vào TS/TSX trừ khi user yêu cầu. Emoji trong **log strings** (`📝`/`✅`/`❌`/...) là customer-facing vocabulary đã agreed, được expected trong `sendLog`/`appendCampaignLog`/block code.
