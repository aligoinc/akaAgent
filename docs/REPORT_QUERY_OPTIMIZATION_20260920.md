# Report query optimization — 20 September 2026

## Changes

- Pending detail pages count matching rows in the database, then fetch only the requested recipients. They no longer download every matching input ID before slicing a page. Reads are scoped by authenticated staff/organization, selected account, executable action and effective schedule (`input.schedule ?? campaign.schedule`). Campaign IDs are partitioned into batches of 200; whole partitions are skipped by their counts.
- Pending detail ordering is now `campaign_id ASC, id ASC`, including export. This deliberately groups each campaign's recipients and makes pagination across partitions stable. Counts remain exact; normal pages may still use OFFSET inside a bounded partition.
- Completed exports use `(created_at DESC, id DESC)` keyset cursors; pending exports use `(campaign_id ASC, id ASC)`. Exports request no exact counts and return their actual exported row count. Preserve PostgreSQL timestamp microseconds verbatim in the cursor. Failures reject the operation rather than returning a partial successful export.
- Completed recipients are embedded via the existing `auto_campaign_details_input_data_id_fkey` relation in each result page, removing extra input lookup requests and the Desktop unbounded IN-list/1,000-row lookup truncation. The left embed retains missing/soft-deleted input history and restricts input metadata through the owning campaign's staff/organization. Web keeps its existing inner campaign ownership guard; Desktop keeps missing-campaign history through a scoped left campaign embed and the authorized root account.
- Desktop coalesces identical in-flight report reads and permits at most two distinct active report loads. Keys include staff, organization, entitlement/capability snapshot and normalized query. Completed results are not cached: a later explicit reload reads fresh data. Current-user context is retained across awaits.
- Export request deadline is 60 seconds; regular details remain 20 seconds. No schema, RPC, index, role/global timeout, polling, or automatic retry was added.

## Read-only production measurements

Production project: `cgjbsmqtfhqvttudyjzq`. Candidate accounts were selected using PostgreSQL statistics and small metadata reads, not a global aggregate scan. Measurements ran sequentially, using the repository queries; Desktop used a standalone isolated process, Web ran on the Fly machine. Authentication context was supplied by the harness after establishing the tenant/account scope. These are **not signed-in UI timings**, CPU measurements, or a load test.

All detail queries used `[2026-01-01T00:00:00Z, 2026-09-20T00:00:00Z)`, 100 rows per interactive page. Baselines are Web `834d8c6` and Desktop `9daba94`.

| Case | Matching rows | Requests before → after | Response bytes before → after | Wall time before → after |
|---|---:|---:|---:|---:|
| Web pending, account 1955, page 25, `zalo_message_stranger` | 6,948 | 12 → 5 | 950,627 → 30,114 | 821 → 459 ms |
| Desktop pending, account 2766, page 70, `zalo_message_stranger` | 8,180 | 14 → 5 | 1,287,348 → 35,824 | 2,597 → 1,318 ms |
| Web completed export, account 1955, `zalo_message_stranger` success | 1,404 | 7 → 4 | 4,457,777 → 4,402,458 | 900 → 660 ms |

Additional cases:

- Desktop completed export, account 457, `fb_message_page_inbox_customer` success: **24,487 rows**, 27 requests, 15,732,264 response bytes, **9,211 ms**, zero exact counts. An intermediate implementation with bounded separate input lookups used 77 requests, 13,141,796 bytes and 19,190 ms. That intermediate implementation is not the original baseline. Embedding reduces round trips while repeating relation metadata, so payload bytes can increase.
- Desktop pending export, account 2766: **8,180 rows and 8,180 unique IDs**, all with target names; 12 requests, 2,291,827 bytes, **2,492 ms**, zero exact counts and no OFFSET.
- Desktop summary, account 457, the same nine-month interval and selected action: 24,487 success, 4,955 failure, 666 pending; 35 requests, 3,218,147 bytes, **5,470 ms**. Summary remains scoped narrow-row aggregation in the application. No aggregate RPC was introduced; broad summaries remain a potential next optimization and are not claimed to be constant-cost.
- A non-executing `EXPLAIN` of a representative deep pending page for campaign 12037 used `auto_campaigns_pkey` and `idx_campaign_input_data_campaign_id`, with a sort within that campaign. This was an equivalent scoped SQL shape, not the exact SQL generated by PostgREST. It does not establish actual database CPU cost.
- An initial verification lookup ordered only by detail ID hit the existing database statement timeout; it was replaced with a scoped account/action/date lookup followed by a primary-key check, without changing timeouts. A one-row live left-embed check with a deliberately nonmatching organization filter returned the historical detail and `report_input: null`, validating metadata filtering without dropping the parent record.

Timings are single samples and depend on network/cache state. An earlier pre-embedding Web export took 2,276 ms despite eliminating exact counts, illustrating this variance. The directly verified improvements are fewer requests, no repeated export counts, no all-ID pending page download, complete result sets and tenant-scoped metadata. No claim of zero database load is made. No campaigns, messages or writes were triggered.
